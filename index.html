Specifications & build scope

ZBOM: every target component is freshly generated from capsule-owned source. Native execution uses Linux x86-64 syscalls directly. Source records and verification results accompany each build.


Native compiler self-hosting, three-stage byte comparisons, ELF64 object generation, native static linking, separately compiled modules and automated regression supervision are operational.


Every executable is ELF64 for x86-64, with 8-byte pointers. Required narrow ELF fields, byte strings and syscall buffers retain their specified widths. The dialect uses 8-byte plain int, 1-byte char and 4-byte explicit signed/unsigned int; narrow loads and returns zero-extend.


The compiler supports functions, recursion, six register arguments, grouped object declarations, globals, pointers, fixed arrays, strings, casts, sizeof, conditional and assignment expressions, sequenced comma expressions, loops, switch dispatch and short-circuit logic. SysV AMD64 register and stack argument spilling (up to 32 parameters), function pointers and indirect calls, true unsigned integer arithmetic, compound unions, compound assignment operators, variadic functions with freestanding <stdarg.h>, and multi-line macros are operational. Zero-SBOM Maximized Capacity: freestanding IEEE-754 soft-float math, pure static archive management, and complete language expansion are under active clean-room development.

# Bootstra.app development checklist — vxvii-horizon

This is the review checklist for the foreseeable development horizon. Keep subsequent passes in vxvii-horizon until its release gates pass; do not advance the version merely because a pass was attempted. Checked implementation items describe bounded capabilities, not a proof that every possible program is correct. Verification results belong to the generated reports.

## Non-negotiable boundaries — review every pass

- [ ] Generate every target component from capsule-owned source. Add no third-party target code, supplied target binaries, target libraries or external target compiler/linker.
- [ ] Emit only Linux x86-64 ELF64 target objects and executables. Keep pointers at eight bytes. Reject foreign formats in memory; never save incompatible binary fixtures.
- [ ] Use direct Linux x86-64 syscalls for target execution and I/O. Preserve the existing dialect widths and documented conversion rules.
- [ ] Keep host prerequisites explicit: the browser generates the initial seed and the Linux kernel executes native outputs. Development compiler, linker and verification tools are project-built. The authorized host shell and filesystem are used only for file I/O and process launching.
- [ ] Deliver one self-contained index.html with procedural assets, one complete bundle download, and no companion resources or network-fetched build inputs.
- [ ] Preserve files on output-path collisions and retain source-to-artifact records. Treat ZBOM as the documented zero-third-party-target-component boundary.

## Priority 1 — correctness and failure behavior

- [ ] Extend the declaration-scope matrix whenever adding a new name category: point of declaration, parameter scope, nested shadowing, prototype scope and conflicts across object/function/constant names.
- [ ] Expand constant-expression boundary coverage: depth, shifts, selected division faults, conversions, duplicate computed labels and nested type dimensions. Keep inactive operands syntax-checked.
- [ ] Review initializer and declaration rollback behavior so rejected source cannot leave a usable partial output.
- [ ] Check every parser recursion path and resource counter at its boundary and one step beyond it. Distinguish storage bounds from evaluation depth.
- [ ] Extend initialization analysis only with a defined control-flow model. The current conservative direct-local checks are not complete alias or path analysis.
- [ ] Add independent expected-value tests for each semantic change; avoid relying only on self-rebuild equality.
- [ ] Exercise malformed input under bounded execution and require precise failure status, diagnostics and absence of output.

## Priority 2 — binary layout and native linking

- [ ] Design separate executable code and writable data segments. Update executable writers, startup mapping, native linker, supervisor and architecture gates together; the current profile can use a writable/executable load segment when data is present.
- [ ] Review arithmetic overflow and extent calculations for every object header, section, symbol and relocation before using offsets or allocating buffers.
- [ ] Extend deterministic linking checks across object order, local-name reuse, alignment padding, multiple data relocations and boundary displacements.
- [ ] Decide how cross-module signature compatibility will be recorded and checked before claiming it. Current ELF symbols do not encode complete C signatures.
- [ ] Consider archive or additional relocation support only when a concrete capsule-owned module requires it; define the accepted format and rejection tests first.

## Priority 3 — source capabilities, driven by native needs

- [ ] Generalize parenthesized declarators and pointer-to-array types with explicit binding and compatibility tests.
- [ ] Add named type aliases or aggregates only with a defined layout, alignment, access and calling convention. Keep them optional until required by a native component.
- [ ] Extend enum scope/tags only after the namespace and lifetime rules are defined; current enumerators are anonymous file-scope constants.
- [ ] Expand constant sizeof beyond a single name or supported type only with unevaluated-expression semantics that cannot emit code or establish initialization.
- [x] Review string-literal concatenation, escape handling and byte-string initializer edge cases in vxv-horizon. Reopen this item whenever the byte-string grammar changes.
- [ ] Add larger call signatures or indirect calls only with a complete stack/register preservation design and native ABI probes.
- [ ] Introduce preprocessing only for demonstrated source needs, without fetching headers or importing outside code.

## Priority 4 — orchestration and execution controls

- [ ] Review partial I/O, interrupted syscalls, short writes, allocation failures and cleanup after child termination.
- [ ] Test deadlines and process-group cleanup for compiler, linker and test children. The supervisor is not a security sandbox.
- [ ] Verify every stage immediately before use and preserve the source, build order and actual verification results in the installed directory.
- [ ] Evaluate an internally implemented cryptographic artifact digest if stronger artifact identity is needed; document that a digest alone does not establish trust in its source.
- [ ] Consider resumable native stages only with validated checkpoints and rejection of stale or mismatched inputs.

## Priority 5 — portability within the specified target

- [ ] Exercise the generated chain on additional Linux x86-64 machines and kernel environments, including constrained memory and unusual filesystem conditions.
- [ ] Record the actual syscall and executable-mapping prerequisites; do not claim every Linux machine is supported without evidence.
- [ ] Keep negative architecture probes entirely in memory on all test hosts.
- [ ] Confirm the page's one-download flow on the intended desktop/mobile browsers; preserve the user-confirmed procedural icon and Bootstra.app title.
- [ ] Recheck home-screen metadata after deployment. A saved HTML copy works offline; hosted home-screen reopening is not guaranteed offline by the single-file shell.

## Release gate — reusable checklist

Reset these boxes for each release. Actual run results are reported separately; an unchecked template box does not imply a failed check.

- [ ] Freshly generate the complete package from the candidate HTML.
- [ ] Run temporary and persistent native bootstrap modes successfully.
- [ ] Require native compiler executable and object fixed points, native linking and supervisor success.
- [ ] Run all packaged behavior fixtures, native positive fixtures and exact-diagnostic source rejections.
- [ ] Exercise new behavior through native object emission and linking, as well as direct executable emission.
- [ ] Audit every packaged and installed target binary for the accepted ELF64 x86-64 profile; rerun in-memory architecture rejection probes.
- [ ] Confirm malformed-object/link rejection, collision preservation and repeated-link determinism.
- [ ] Check the single download, generated manifest/icons, title/version identity and absence of external resources.
- [ ] Create a hosting ZIP containing only root index.html; verify CRC and exact extracted bytes.
- [ ] Save the release and report measured results and material remaining limitations. A finite test suite and fixed point are evidence, not proof of no flaws.

## Iteration rule

Choose a concrete need or reproduced defect, state its semantics, implement it inside the capsule, run focused checks, then run the release gate. Stop expansion to resolve any failing gate. Carry unfinished items forward explicitly. Do not add a capability just to imitate another toolchain, and do not start vxvi-horizon until the vxv-horizon result is reviewable.
